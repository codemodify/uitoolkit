## BUG 1: Focused text field spins the app in an IME feedback loop (~3500 repaints/s, >100% CPU) on Wayland/KWin
- app: gallery (all apps with TextField/TextArea/NumberField) ; severity: critical ; confidence: high ; partialOnly: false
- repro: rig 12 (nested KWin, Wayland backend). Launch gallery, `in.sh 12 move 300 585 sleep 150 click` (focus Name). Measure /proc/PID/stat: idle 0 ticks/3s -> 237 ticks/3s focused (app ~108% CPU while KWin ~10%). Instrumented build (overlay logging dispatch/frame) shows EventIMEPreedit(kind=13, empty text) x2 + FRAME(rects=Name field) repeating every ~0.3ms: ~11000 preedit events and ~2000 frames in 0.63s. Stops as soon as focus leaves the text widget.
- actual: busy loop; app re-renders the focused field thousands of times per second; also starves presentation (see BUG 2) so other widgets' changes are skipped/partially shown.
- expected: no events/paints while idle with a focused field (only caret blink ~2/s).
- rootCause: feedback loop between app and compositor text-input-v3: (1) platform/wayland_linux.go:3179 uitkWlTIDone pushes an EventIMEPreedit (empty text) for EVERY zwp_text_input_v3.done, even when preedit/commit/delete are all unchanged; (2) app/window.go:498-501 handles EventIMEPreedit by calling t.IMEPreedit(...) and then w.syncIMECursor(); (3) syncIMECursor (app/window.go:352-355) calls SetIMEEnabled(true)+SetIMECursor(...), and platform/wayland_linux.go:1707-1718 SetIMECursor unconditionally sends set_cursor_rectangle + zwp_text_input_v3.commit (also wlEnableTextInput 3216-3222 commits); (4) the compositor answers every commit with done -> goto (1). Additionally widgets/textfield.go:173-188 IMEPreedit Invalidate()s even when the preedit is unchanged ("" -> ""), so each loop iteration repaints the field.
- proposedFix: break the loop at every layer: in uitkWlTIDone only emit EventIMEPreedit when (imePre, caret) differs from the last emitted preedit (track c.lastPre); in SetIMECursor cache the last committed rect and skip set_cursor_rectangle+commit when unchanged (same for enable when already enabled); in TextField/TextArea.IMEPreedit return early when s == t.preedit && caret == t.preeditCaret.
- files: platform/wayland_linux.go, app/window.go, widgets/textfield.go, widgets/textarea.go

## BUG 2: A frame painted while a wl_surface.frame callback is pending is silently dropped (GPU path) -> stuck pressed buttons, popups that never appear / appear as a slice
- app: all (gallery repro) ; severity: critical ; confidence: high ; partialOnly: false (also with UITK_PAINT_FULLFRAME=1)
- repro A (no text field focused): `in.sh 12 move 366 331 sleep 400 down sleep 5 up sleep 600` on "Secondary": button stays painted pressed and status bar stays "Ready." (should be "Secondary clicked") until the pointer moves away; same with FULLFRAME=1 (shots d01, d11, d12). Probe log: MouseDown->FRAME presented; MouseUp 5ms later -> FRAME rects=[button,status] -> skipped, never re-presented.
- repro B (my area): click Name field, then `move 543 730 click` on the Paint engine combo: popup does not appear at all (1s+), after moving the pointer onto another widget only a 30px slice of the popup appears inside the Name field rectangle (shots b03,b04,c01-c04,zc04). Probe: `FRAME full=true popup=true` was produced at the click but never reached the screen.
- rootCause: platform/wayland_linux.go:1841-1843 wlSurface.Present returns nil without presenting when s.framePending (GPU/EGL path). app/window.go:908-911 then treats the frame as delivered (`w.dirty.Reset(); w.full = false`), and paintengine2d gpu_linux.go:1382 SetPresentDamage of the next frame overwrites the pending rects, and recordFrameDamage never records the dropped frame's damage for buffer-age repair. uitkWlFrameDone (wayland_linux.go:1924-1929) only clears framePending and does not schedule the deferred present, so the skipped content stays off-screen until an unrelated repaint, and then only the new damage (plus buffer-age history) is blitted from the FBO -> partial slices of the popup.
- proposedFix: when Present is skipped for pacing, keep the damage: either return a sentinel (ErrFrameDeferred) so Window.frame keeps w.dirty/w.full, or have wlSurface accumulate skipped rects (nil => full) and union them into the next Present, and on uitkWlFrameDone post a wake/Expose so the loop presents the accumulated damage. In paintengine2d, SetPresentDamage should union with not-yet-presented rects instead of replacing them.
- files: platform/wayland_linux.go, app/window.go, pe/gpu_linux.go, pe/scene.go

## BUG 3: Popup/combo menu hover highlight leaves stale slivers and is drawn truncated (partial redraw)
- app: gallery (combo popup; same code for all PopupMenus) ; severity: minor ; confidence: high ; partialOnly: true
- repro: UITK_BACKEND=x11 (avoids BUG 1/2 noise) ; open Paint engine combo (`move 543 730 click`), `move 300 640` (hover "Software raster"), `move 300 675` (hover "Offscreen pixmap") -> navy slivers (~5px left, ~7px right) of the old "Software raster" highlight remain, and the new highlight is ~13px narrower than a fully painted one (shots x02,x03, zx2, zx4). With UITK_PAINT_FULLFRAME=1 the same steps are clean (x13, zx5).
- rootCause: style/look.go:563-567 menuItemHighlightBounds widens the highlight to item.Min.X-PadL+2 .. item.Max.X+PadR-2 (PadL 8 / PadR 10, style/menu.go:58-59), but widgets/menu.go:798-803 invalidateRow only damages rowBounds(i).Inset(-1) (rowBounds = PadL..PadL+innerWidth, menu.go:658-665). The hover change (menu.go:805-833) repaints only that narrower box, so the old highlight's ends are never erased and the new one is clipped by the damage rect.
- proposedFix: invalidate the full-width row: in invalidateRow use XYWH(0, rowTop-OffsetY, LocalBounds().Dx(), rowH).Inset(-1) (or ask the look for the highlight bounds), so damage covers everything DrawMenuItem paints.
- files: widgets/menu.go (invalidateRow), optionally style/look.go

## BUG 4: Default theme (Classic 95 Dark): focused Name/Columns/TextArea have an invisible caret and no visible focus indicator; Paint engine combo shows none either
- app: gallery (all apps using the default dark look) ; severity: major (keyboard a11y) ; confidence: high ; partialOnly: false
- repro: UITK_BACKEND=x11 (clean paint), press Tab repeatedly (shots tab9..tab13, ztab.png): when Name / Columns / Paint engine get focus nothing changes except a caret that is practically invisible; click in Name: caret pixels (6,6,110) on field (31,31,31) (shot a01, x=262..263,y=585). Contrast: caret #000080 vs field #1f1f1f = 1.03:1, focus border #000000 vs field = 1.27:1 (WCAG needs 3:1). Combo after keyboard Up (g05, zg5.png) looks identical to unfocused.
- rootCause: (a) caret colour is palette Accent: style/look.go:396 (TextField) and :1321 (TextArea) `Fill(p.Accent)`; dark theme accent is #000080 (style/themes/dark/theme.json). (b) the focus ring is drawn outside the widget: style/look.go:362 (TextField), :993 (ComboBox), :1249 (TextArea), :258 (Button) call DrawFocusRing(b.Inset(-2)); for classic-3d DrawFocusRing (look.go:434-435) strokes b.Inset(1) = bounds.Inset(-1) with a 1px pen, i.e. entirely outside the bounds, but widget/paint.go:28 and widget/scene.go:258 clip each widget to its local bounds before Paint, so the ring is clipped away (only a 1px column survives on the right edge due to fractional bounds, shot za01b). (c) the remaining cue, faceColors focus border (style/chrome.go:223-229), is t.Focus.Border = #000000, invisible on #1f1f1f.
- proposedFix: caret: use p.Text (or a per-theme Caret token) instead of Accent; focus ring: draw inside the bounds (b.Inset(+1..2)) for fields/combos/buttons, or let PaintTree/RecordTree clip to bounds.Inset(-focusMargin) for focusable widgets (and invalidate that margin); dark classic theme: focus/focusBorder must be a light colour (e.g. #ebebeb dotted like Win95).
- files: style/look.go, style/chrome.go, style/themes/dark/theme.json, widget/paint.go, widget/scene.go
