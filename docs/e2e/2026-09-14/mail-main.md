## 1. Attachment (paperclip) glyph renders as a solid capsule/tofu box everywhere (header, rows, attachment list)
- app: mail (engine-level glyph fallback in style/) ; severity: minor ; confidence: high ; partialOnly: false
- repro: launch mail; look at list header col 2 and rows with attachments, and the preview attachment rows ("📎  mail-shortcuts.txt"). Zoom: shots/z_clip.png. Headless: rig/16/glyph/main.go renders "📎" with style.BakeFont(40) -> solid filled rounded bar (no hole).
- actual: a solid white rounded vertical bar (reads as a tofu/notdef box) instead of a paperclip.
- expected: a recognisable paperclip (or at least a hollow outline).
- rootCause: style/symbols.go:55-64 fallbackPaperclip builds the "clip" as two AddRoundRect contours (outer + inner). paintengine2d AddRoundRect (paintengine2d/path.go:146-177) always emits a clockwise contour, and the atlas bakes glyph paths with paintengine2d.Fill() (style/opentype.go:532, FillRule zero value = FillNonZero). Same-direction inner contour has winding 2 -> filled, so no hole; result = solid capsule. (Titillium lacks U+1F4CE so rasterize() -> symbolFallback, opentype.go:379-381.)
- proposedFix: build the paperclip as a real outline: either emit the inner contour counter-clockwise (reverse point order / add a Path.AddRoundRectCCW helper) or stroke a paperclip centre-line (nested U-curves) into an outline via paintengine2d stroker before baking; alternatively set FillRule=FillEvenOdd for fallback paths in blitPath/bakeCell. Add a golden test that the glyph has an interior hole.
- files: style/symbols.go, style/opentype.go (optional even-odd), style/tablecell_test.go (test)

## 2. After any full-frame repaint (folder switch, layout change), the next small repaint shows a 2-frames-old picture: wrong message list, multiple folders highlighted (GPU buffer-age history drops full frames)
- app: mail (engine bug, affects every app) ; severity: critical ; confidence: high ; partialOnly: true
- repro: run.sh 16 mail; in.sh 16 move 100 148 sleep 300 click sleep 500 move 100 172 sleep 300 ; shot. (Drafts clicked, then hover Sent.) Second repro: move 100 172, click (Sent), move 100 268 (hover Junk).
- evidence: shots/ct1.png (t01/t02/t03), shots/cg1.png (g02/g03/g04), full-frame oracle shots/cff1.png (correct). diff t01 vs t03: only the hovered Sent row differs -> t03 == frame from two swaps ago + current damage.
- actual: after clicking Drafts the list shows Drafts; merely hovering the next folder makes the window show the Inbox list again with Inbox+Drafts+Sent all highlighted; next hover flips back to correct content (alternates between swapchain buffers).
- expected: current state (Drafts list, one selected + one hovered folder).
- rootCause: paintengine2d/gpu_linux.go PresentRects: for a full-surface present (rects nil/empty — every frame after w.full / relayout, app/window.go:865-868 paintRects returns nil) it calls d.recordFrameDamage(rects) (gpu_linux.go ~1497 / 1506-1513) which pushes an EMPTY slot onto the age ring. The next partial present gets EGL buffer age 2 (KWin/Mesa swapchain) and damageForAge (1517-1526) unions this frame's rects with the previous ring slot = nothing, so the scissored FBO->window blit (blitDamageRects) repaints only the two hover rows; the rest of the back buffer still holds the frame from 2 swaps ago. (Folder click -> refreshAll -> RequestLayout -> w.laid=false -> fullInvalidate -> nil rects.)
- proposedFix: in PresentRects/recordFrameDamage record a full-surface rect (XYWH(0,0,d.w,d.h)) when rects is empty (and in the !window branch), or keep a per-slot "full" flag and make damageForAge return nil/force full blit if any frame within `age` was full. Add a unit test: full present followed by partial present with age 2 must blit full surface.
- files: pe/gpu_linux.go (PresentRects, recordFrameDamage, damageForAge), pe/gpu_test (new test)

## 3. Frames are silently dropped while a Wayland frame callback is pending; the final state after fast pointer motion (or a quick click) is never presented
- app: mail (platform bug, affects every app on Wayland) ; severity: major ; confidence: high ; partialOnly: false
- repro: run.sh 16 mail (also with UITK_PAINT_FULLFRAME=1); in.sh 16 move 450 300 sleep 300 ; in.sh 16 move 450 330 move 450 360 move 450 390 move 450 420 move 450 450 move 450 480 move 450 510 move 450 540 move 450 570 move 450 600 sleep 600 ; shot. Wait any time: unchanged. Nudge within the same row: unchanged. Press Tab (forces an unrelated repaint): the correct hover row (y=600) suddenly appears.
- evidence: shots/cfm.png, cfm2.png (partial: hover stuck on row at y~356 while pointer at 600), shots/cffm.png (FULLFRAME: stuck at y~468), shots/cffm2.png (after Tab: correct row at y~600).
- actual: hover highlight stays on an intermediate row the pointer left long ago; no row under the pointer is highlighted.
- expected: the last state is always presented once the compositor is ready.
- rootCause: platform/wayland_linux.go:1836-1843 (wlSurface.Present GPU branch) returns nil without presenting when s.framePending && !s.frameOverdue(). app/window.go:894-897 (Window.frame) ignores the result and resets w.dirty / w.full, so the frame is lost; uitkWlFrameDone (wayland_linux.go:1923-1929) only clears framePending and never schedules a repaint. In partial mode it is worse: GPUDevice.SetPresentDamage (pe/gpu_linux.go:1382-1392) overwrites the stored rects of the skipped frame at the next DrawSceneDamage, so the dropped region is not blitted by later frames either (only rescued accidentally by buffer-age history).
- proposedFix: make throttling non-lossy: Present should report "deferred" (e.g. return platform.ErrPresentDeferred / bool) and Window.frame must keep the damage (don't Reset dirty; or accumulate into w.pendingPresent) and retry; uitkWlFrameDone should WakeLoop()/queue an EventExpose so the app re-presents the accumulated damage. In paintengine2d, SetPresentDamage should union with an unconsumed presentRects (presentSet still true) instead of replacing it, and treat a pending full present as full.
- files: platform/wayland_linux.go (Present, uitkWlFrameDone), platform/wayland_egl_linux.go, app/window.go (frame), pe/gpu_linux.go (SetPresentDamage)
- extra evidence (#3): minimal probe rig/16/probe2 (custom widget logging MouseMove+Paint): log shows every motion processed and the last Paint "hover=12" 1.2 ms after the previous paint, but shots/pr01.png still shows row 4 highlighted -> the painted frame was never presented (dropped by frame-callback throttle), not an input problem.

## 4. Message list hover highlight sticks to the old row after wheel scrolling (row under the pointer not highlighted)
- app: mail (widgets/table.go; same pattern in TreeView, ListView, CardList) ; severity: minor ; confidence: high ; partialOnly: false
- repro: in.sh 16 move 450 500 sleep 400 ; shot ; in.sh 16 wheel 1 sleep 500 ; shot. (also with UITK_PAINT_FULLFRAME=1)
- evidence: shots/cw2.png (partial), shots/cfw.png (FULLFRAME) — highlighted row scrolls up ~2 rows with the content while the pointer stays at y=500; with wheel 3 the highlight disappears entirely (shots/cw.png) until the mouse moves.
- expected: after scrolling, the row now under the pointer is hot (Qt/GTK re-evaluate hover on scroll).
- rootCause: widgets/table.go:706-718 TableView.MouseWheel changes OffsetY and Invalidates but never recomputes t.hovered from e.Pos (which the wheel event carries), so the stale row index keeps painting hot (paintRow uses row == t.hovered, table.go:420). Identical code in widgets/tree.go:419-431, widgets/list.go:233-245, widgets/card.go:383-395.
- proposedFix: after a successful scroll set t.hovered = t.indexAt(e.Pos.Y) (and hoverCol=-1 / header check) before Invalidate; same in TreeView/ListView/CardList (and the scrollbar-thumb drag path in MouseMove already recomputes nothing either — apply there too).
- files: widgets/table.go, widgets/tree.go, widgets/list.go, widgets/card.go

## 5. Hovered rows are pixel-identical to the selected row (message list, folder tree, attachment rows) in every shipped theme
- app: mail (style; affects all list/tree/table widgets) ; severity: minor ; confidence: high ; partialOnly: false
- repro: launch mail (default dark theme); move 450 216 (hover "Thread: lunch plans") -> it paints exactly like the selected "Welcome…" row; move 100 148 over "Drafts" in the tree -> looks selected like "Inbox (39)". px: both rows (0,0,128) fill + identical bevel line.
- evidence: shots/cw3.png (table: two navy rows, one hovered one selected), shots/ct1.png top panel (tree: Inbox selected + Drafts hovered identical)
- expected: hover is a lighter/tinted hot-track distinct from selection (Qt/GTK/Win32 listviews), so the user can tell which message/folder is actually selected while the pointer is elsewhere.
- rootCause: style/chrome.go:210-217 faceColors roleRow hot -> fill = t.Hot.Fill (alpha only reduced for BevelNone/Fluent/SoftShadow, not classic-3d or luna-hottrack) and border t.Hot.Border; style/chrome.go:236-239 selected -> t.Selected.Fill. All shipped packs set hotFill==selectedFill and hotBorder==selectedBorder (style/themes/dark|light/theme.json: #000080/#000040; luna: #c1d2ee/#316ac5). DrawTableCell (look.go:1156), DrawTreeRow (look.go:738), DrawListRow (look.go:460) all route hover through this.
- proposedFix: give roleRow hover its own treatment independent of Hot.Fill, e.g. fill = Selected.Fill.WithAlpha(0.25-0.35) (or Lerp(surface, 0.3)) and no selection bevel, or add a rowHover token to the packs; keep full Selected.Fill only for StateChecked.
- files: style/chrome.go, style/themes/*/theme.json (optional rowHover token), style/tokens.go

## 7. Hover state sticks forever when the pointer leaves the window (no pointer-leave event on Wayland or X11)
- app: mail (platform + app; every app) ; severity: major ; confidence: high ; partialOnly: false
- repro: UITK_PAINT_FULLFRAME=1 run mail; in.sh 16 move 450 300 sleep 400 (hover "Quick Filter pin states") ; in.sh 16 move 600 856 sleep 600 (below the window) ; shot ; in.sh 16 key 15 (Tab forces repaint) ; shot. Same when leaving through the KWin title bar/decoration or into another window. Seen first as two highlighted rows in shots/k02.png.
- evidence: shots/cpl.png (pl01 hovered, pl02 after leaving, pl03 after a full repaint: row still hot)
- expected: leaving the surface clears hover (Qt leaveEvent / GTK leave-notify), tooltips cancel, cursor state resets.
- rootCause: platform/wayland_linux.go:2528-2534 uitkWlPtrLeave only zeroes c.ptrSurf and pushes no event; platform/event.go:113-130 has no EventMouseLeave kind; app/window.go dispatch (449-567) only clears w.hover on EventFocusOut (476-485). X11: platform/x11_linux.go:79-80 event_mask lacks EnterWindowMask|LeaveWindowMask so LeaveNotify never arrives either.
- proposedFix: add platform.EventMouseLeave; push it from uitkWlPtrLeave (for the surface that had c.ptrSurf) and from X11 LeaveNotify (add LeaveWindowMask); in Window.dispatch handle it like the FocusOut hover block: w.hover.MouseExit(); w.hover=nil; dismissTooltip; reset cursor (keep capture while a button is held).
- files: platform/event.go, platform/wayland_linux.go, platform/x11_linux.go, app/window.go

- expected: Ctrl toggles, Shift extends a range, Shift+Up/Down extend, Ctrl+A selects all (Thunderbird / any listview); bulk Delete/Archive/Mark read/Star then act on all.

- proposedFix: add a selection set to TableView (SelectedRows map / IsSelected func + anchor), honour Ctrl/Shift on press and Shift+arrow/Home/End on keys, Ctrl+A select-all; expose OnSelectionChange(rows); in mail wire it to s.selected (clickRow add/range) and paint all selected rows; bind Ctrl+A to selectAll and Invalidate the table.
- files: widgets/table.go, examples/mail/mailapp/ui.go
